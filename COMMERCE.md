# Lumina Stream commerce implementation

## Cancellation and unresolved claim correction

The source now initializes the status selector from the saved order and displays API failures inline without discarding the selected status or reason. Successful changes reload the order from D1; dashboard/list views load current D1 state on navigation.

Cancellation requires a reason, no fulfillment or subscription history, and an unpaid order. A paid test order additionally requires the explicit administrative test-cancellation checkbox; its payment and invoice history remain unchanged. Real paid orders require financial reconciliation/verified refund, and closed orders cannot be reopened through the status selector. Repeated identical status updates do not duplicate audit records.

Pending claims may be rejected on closed orders with a recorded reason, reviewer and timestamp. Approval on closed orders is blocked. A reviewer reporting actual receipt must use separate financial reconciliation rather than reject the payment as unpaid; this change does not implement or send refunds. Closed order/payment states and original records are preserved.

`migrations/0003_closed_order_reviews.sql` replaces only the rejection trigger and adds a transactional closed-order approval guard. It does not delete records or rewrite old migrations. It was tested using isolated local D1; production application requires approval. After approval, apply the pending migration with `npx wrangler d1 migrations apply lumina-db --remote`, then use the existing approved build/deployment workflow to publish source changes. Do not push an auto-deployed branch before approval. Existing `dist` and `.worker-build` outputs were not rebuilt for this fix.

Validation: `node --test tests/*.test.mjs` passes 17 tests, including UI event behavior, persistence, open/closed claim rejection, test/real paid cancellation safeguards, subscription protection and duplicate audit prevention.

Implemented locally in the existing repository. **Production has not been deployed or reconfigured.** The existing `.openai/hosting.json`, project ID, public audience and hosted database remain unchanged.

## Existing architecture and changes

The original site is a static, dependency-light HTML/CSS/JavaScript storefront generated by `source/build.mjs`. Its products and prices come from `source/pricing.json`. It had no backend, database or administrator authentication; checkout saved plan selections in browser storage.

The same storefront, pricing table, routes, English/French pages, theme, animation settings, SEO metadata and images remain. The Worker API imports the original price table and ignores customer-supplied totals. Checkout now creates durable database orders. Browser storage is used only for existing display preferences, not orders, contact details or payment claims.

The previous plan-card work is retained: independent duration/device controls, differentiated plan features, and shared natural-height text-link styles.

## Local run

Requires Node 22.13+ with `node:sqlite` (tested using Node 26).

```powershell
npm ci
npm run build
npm run setup:local
npm start
```

The local URL defaults to `http://localhost:4173`. Set `PORT` to choose another port. The server binds loopback, applies pending local migrations, and stores records in `.local/lumina.sqlite`; private PDFs are in `.local/private/invoices/`.

`setup:local` creates `.env.local` only if missing. Local login email is `admin@localhost.invalid`. Read `LOCAL_ADMIN_PASSWORD` in that private file to obtain the generated local password. The file also holds the salted password hash and encryption/signing secrets. It is ignored by Git and is never bundled into frontend files. It is not a production credential. Keep `.local` and `.env.local` private and backed up when using local data.

Customer routes: existing checkout, `/order/` and their `/fr/` counterparts. Admin routes: `/admin/`, `/admin/orders/`, `/admin/payments/`, `/admin/invoices/`, `/admin/customers/`, `/admin/subscriptions/`, `/admin/settings/`, all with French counterparts.

## Database migration

Apply `migrations/0001_commerce.sql` once to a **new commerce D1 database** before serving API requests. It creates customers, orders, payment quotes, claims, invoices, subscriptions, encrypted settings, sessions, rate limits, audit records and email-delivery records, plus constraints and state-protection triggers. No production migration was applied.

Local previews apply it automatically and record `_migrations`; automated tests use isolated temporary SQLite databases. Do not edit this migration after applying it to a shared/production database; append a new numbered migration instead.

Database operations use D1 prepared statements and atomic `batch()` transactions. Creation inserts the customer, order, pro forma invoice and audit event together. Unique indexes enforce idempotency, one approved payment per order, one verified blockchain transaction per network, one activation per order, and one final/full-credit document per order.

## Cloudflare configuration, after deployment approval

The tracked Wrangler configuration now targets the existing relay-clone Worker with DB bound to lumina-db (907cf85d-f371-41ab-aeaf-aeb5edac386c) and private R2 binding INVOICES bound to lumina-invoices. Runtime secrets:

| Name | Purpose |
| --- | --- |
| `ORDER_SECRET` | At least 32 random characters, signs repeatable idempotent order access capabilities |
| `SETTINGS_KEY` | At least 32 random characters, AES-GCM encryption for payment settings |
| `AUTH_MODE` | `sites` for trusted Sites identity; `password` for direct Worker hosting |
| `ADMIN_USER_IDS` | Comma-separated allowed Sites user IDs when using Sites authentication |
| `ADMIN_EMAIL` | Administrator identity for password mode |
| `ADMIN_PASSWORD_HASH` | Salted PBKDF2-SHA256 hash from `passwordHash()`; no plaintext production password |
| `EMAIL_API_KEY` | Optional Resend API key for invoice delivery |

For Sites hosting, administrator authorization uses only the platform-authenticated user ID and an explicit ID allowlist. Platform sign-in establishes identity, not permission. **Do not use `AUTH_MODE=sites` on a raw Worker endpoint where callers can supply the identity headers.** Direct Worker hosting uses the password/session mode instead. Configure HTTPS before exposing password login. `LOCAL_DEV=true` is only for the loopback preview and must not be set in production.

Password sessions expire after eight hours and use HttpOnly, SameSite=Strict cookies, plus Secure on HTTPS. Mutations require same-origin JSON requests with a custom header; password-authenticated administrator mutations also require a session-bound CSRF token. Login and order creation are rate-limited in the database. Use edge rate limiting as additional protection before accepting public live orders. Enforce account recovery/credential rotation and an operator-approved retention/backup policy before launch.

## Payments and operator configuration

Settings default to `mode: test`. Both live methods default to disabled. No wallet, eligible receiving account, legal seller identity, tax registration or tax rate is invented. Administrative settings are validated and encrypted at rest; only public payment instructions for an enabled method are returned to the customer. Private wallet keys are neither required nor stored.

Test Interac uses `test-only@example.invalid`. Test crypto uses `TEST-ONLY-NOT-A-PAYMENT-ADDRESS`; QR codes encode this non-payment string. The fixed test exchange quote is labelled simulation-only. No test instruction can be used to send real funds. Test/live mode is stored on each order; a mode change requires a new order. Verified test payments do not count toward live verified revenue.

Before live instructions can be returned:

1. Configure actual legal seller name/address/email, and explicitly configure the applicable tax label/rate in basis points. The implementation supports one configured tax rate for this Canada-only storefront; multi-jurisdiction automatic tax determination is not implemented. The operator must configure the correct rate for the offered service/customer scope before live use.
2. Interac: configure recipient name/email, explicitly enable the method, and attest that the eligible receiving account has been independently verified.
3. Crypto: explicitly enable it, complete legal and operational approval, and configure a verified recipient address for each supported token/network pair. Supported pairs are USDT on Ethereum/Polygon/Tron and USDC on Ethereum/Polygon. Token contract authenticity and network support must be independently checked by the operator.
4. Configure a token-specific `cadPerToken`, `quotedAt` timestamp and quote source for USDT/USDC. Quotes older than 15 minutes are rejected. Customer quotes last ten minutes and amounts round upward to six decimals. Rates are administrator-supplied, not a claim of live automated market pricing. Refresh them operationally before live checkout; an automated exchange-rate feed is not configured.

Claims can be recorded after quote expiry so a customer who already transferred is not silently discarded. Expired-quote submission is noted in the audit log and must be resolved during independent review.

The administrator must inspect the bank ledger or blockchain explorer independently, then record receipt, receiving account/address, amount and currency checks. Crypto additionally requires correct token contract, network, success and finality checks. An independent bank/explorer reference is mandatory. Customer claims never mark orders paid. These are **manual verification records**, not automated bank reconciliation or blockchain confirmation monitoring.

Payment state, fulfillment state and subscription state are separate. After approval, manual provisioning/activation records an external fulfillment reference and activation/expiry dates. It does not create credentials at an IPTV upstream provider. Duplicate activation returns the existing subscription. Calendar-month expiry clamps month-end dates; trial expiry is 24 hours. Expired status is computed from the stored expiry.

## Tracking, invoices and email

Orders have a unique public identifier, a server-generated `LUM-YYYY-NNNNNN` reference and a 256-bit access capability. Only a hash of the capability is stored. Private tracking links carry the capability in the URL fragment, not query parameters or server request logs. The browser sends it as a Bearer header for authorized reads/PDF downloads. Anyone holding the link can access that order; keep it private. There is no unauthenticated email-based order lookup.

Invoice documents have immutable seller/customer/product/tax/payment snapshots. A global database ledger allocates monotonically increasing document IDs, displayed with `PF`, `INV` or `CN` prefixes and the year. Pro forma documents are payment requests, not evidence of payment. A final invoice is created atomically with verified payment. Test PDFs are labelled test mode, and unconfigured seller information is explicitly identified, not fabricated.

PDFs are generated on demand and stored privately in R2. Every download rechecks order capability or admin authorization. No public bucket URL is returned. The full-refund action creates a credit note, marks the final invoice credited, records a verified refund reference, and cancels the subscription. It records an independently completed refund; it does **not** send a bank/crypto refund. Partial credits and invoice reissuance are not implemented; corrections use a full credit and a new corrected order.

Invoice email delivery is available through Resend when an operator-provided API key and verified sender are configured. Email credentials were not supplied, so real delivery was not attempted. Delivery is administrator-triggered and uses provider idempotency keys to reduce duplicate sends. Configure the verified sender and appropriate customer-notification policies before use.

## Subscription delivery and dashboard cards

Migration `0002_subscription_delivery.sql` adds encrypted provider-access records. On a paid, fulfilled order with an active subscription, the administrator can save Xtream server URL/username/password or an M3U URL and setup instructions, then explicitly email a private order-access link. Credentials never appear in the email, audit records or general order response. The customer must present the private order capability and explicitly reveal access; expiry/cancellation/refund blocks disclosure. Provider accounts must still be created in the operator's own panel. Email sends are manual and version-idempotent. Updating credentials resets delivery status so the new version can be sent.

Dashboard cards now link to matching table filters. Revenue and monthly reporting show live and simulated payments separately. The current local example has CAD 365 simulated revenue and CAD 0 live revenue.

Localhost tracking links only work on the computer running the server. A public HTTPS deployment is required before emailing live subscription access to real clients. The Resend onboarding sender remains for owner testing; customer delivery needs a verified sending domain. No client access email was sent during this implementation. Nine integration tests now include encrypted access, authorization, expiry, secret-free mocked email, duplicate-send protection and revenue/card filter accuracy. Production was not deployed. Apply the second migration before a later approved server deployment.
